description: Find, compare or extend fp-game-alpha game-development studies by question, following actual sources and stated evidence limits. Use for exploratory questions and entrusted studies; a request to explore does not imply game implementation.
---

Start with the user's question and requested result. Read [the purpose and current scope](../../../docs/purpose.md) for the role of the public reference and its long-term aims. Use [the reading guide](../../../research/README.md), then select relevant entries in [the technical catalog](../../../research/catalog.json). Its topic IDs cover rules/time, worlds, graphics, music, logic/arrays, composition, assurance and practice. Read selected guides and the actual implementation/tests or versioned external sources needed to assess the claim; do not load the whole collection. [Coverage](../../../research/coverage.md) records the inspected source set and gaps.

Keep the catalog's distinctions: `implemented` has a concrete implementation; `example` demonstrates a bounded case; `experiment` tests an alternative; `question` remains open; `historical` preserves a dated result. These describe the result, not a confidence ranking or an adopted architecture. Check each entry's `evidence` and `limits`: code, finite tests, a device observation, a person's judgment and reuse in another game are different evidence.

Compare what the question needs with the source's inputs, outputs, time/observation boundary, approximation and ownership. Retain counterexamples and application choices. For example, Stillroom's seeded terrain does not remember player edits, its environmental sound retains phase history, and its grass arithmetic does not compile arbitrary Haskell to a GPU. APL, Prolog, Free and categorical studies need not become a game's engine, language or DSL. Use public sources and recorded provenance; no private memory or original conversation is required.

For an entrusted study extension, keep the defining question and a discriminating example or counterexample, inspect the real consumer, and report only the checks actually run. Preserve original authorship, versions, licenses and negative results. Put the new explanation or executable evidence beside its study; update the catalog's guide, sources, status, evidence and limits when they change. Follow [site maintenance](../../../site/README.md) for generation/checks and the repository's publication/provenance rules for source exports. A source in another maintained app can remain canonical there.

For a new playable game use [new-game](../new-game/SKILL.md); for an existing Haskell game use [fp-gamedev](../fp-gamedev/SKILL.md). Use [game-platform](../game-platform/SKILL.md) for an entrusted host/build task and [learn-code](../learn-code/SKILL.md) for explaining the current game's code. An exploratory request can finish with a grounded explanation, comparison or experiment proposal; these links do not authorize starting a separate implementation.
