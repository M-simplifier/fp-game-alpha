# このリポジトリの役割

fp-game-alphaは、ゲーム開発の技術探究と実践から得た知見や実装を集め、誰でも辿れる形に整理した公開リファレンスです。

ゲームを作る中で生まれた問いを調べ、設計を考え、コードを書き、実際に確かめる。そうして積み重ねてきた成果と、いま取り組んでいることを一つの場所にまとめています。

長期的には、具体的なゲームライブラリ・エンジン・システムを育てていくことを目指しています。その形が定まるまで、途中で得られた知見も使える形で公開します。完成した成果だけでなく、実験、教材、検証結果、未解決の問いも、このリファレンスの大切な内容です。

<a id="研究を見渡し実装まで辿る" name="研究を見渡し実装まで辿る"></a>

## 問いを見渡し、実装まで辿る

純粋関数型アーキテクチャは、技術探究の出発点です。

ゲームの状態遷移と参加者の観測から、Haskellによる描画、自然物と風景の生成、連続する音楽、Prologによる関係の記述、APLによる配列の計算、Freeモナドや圏論を用いた解釈と合成へと、関心は広がってきました。

これらの技法には、それぞれ異なるものの見方があります。あらかじめ役割を決めて一つの仕組みに押し込むのではなく、何を自然に表せるのか、どのような操作が可能になるのか、何を失うのかを、具体的な実装を通して確かめていきます。

技術目録には、関心のある問いから、説明、実装、教材、検証結果へ進める入口を置きます。過去の蓄積と現在の試みを主題ごとに整理し、公開された資料だけで考え方や根拠を辿れるようにします。収録した資料と出典の範囲は [coverage](../research/coverage.md) に記録します。

作例は、動かせる成果であると同時に、設計を試すための材料でもあります。

短いゲームの一つの操作、大きなシミュレーションの資源管理、生成される風景、時間に沿って続く音楽。それぞれの題材が、異なる設計上の難しさを明らかにします。

複数の作品に共通する構造が見つかることもあれば、共通化すると失われる重要な違いが見つかることもあります。そのどちらも、次の設計に役立つ知見として残します。

## 読むことと、使うこと

ゲーム開発の技術や考え方を深く知りたい人には、主題別の目録と、具体例から理解できる教材を用意します。

Haskellを初めて読む人でも、一つの操作が状態をどう変えるかを追うところから始められます。さらに深く調べたい人は、実際のコード、数学的な条件、反例、検証方法、参考文献へと進めます。

ゲームを作りたい人には、自分の企画をAIへ渡し、制作を始めるための手順とスキルを用意します。

基本となる順序は、**人間の意図 → AIによる設計・制作 → 再現可能なツール** です。

まず人間が作りたいゲームを考え、AIが必要な知見を選び、設計・実装・検証を進めます。繰り返し使えると分かった部分は、ライブラリやツールとして整えていきます。

目録に載っている技法や、既存のテンプレートだけが作れるゲームの範囲を決めるわけではありません。企画に必要なものがまだなければ、調べ、考え、実際の作品で試します。

ゲームの制作と技術探究は、互いに切り離された活動ではありません。新しいゲームを作ることが技術への問いを生み、その問いに取り組むことで、次のゲームを作るための知見が育っていきます。

## 実装の正本と説明を分ける

実装の構成や挙動については、実際のソースコードを正本とします。検証結果については、実行した検査とその条件を根拠にします。

ドキュメントは、コードに書かれている情報を別の場所へ複製するためのものではありません。

なぜその設計を選んだのか。どのような条件で使えるのか。どこで失敗するのか。ほかの方法と比べて何が変わるのか。そうした、コードだけでは伝わりにくい理由や意味を説明するために用意します。

関数一覧や設計情報の重複を増やさず、必要な説明から実際のソースへ辿れる構成を目指します。

別の公開作品が実装の正本を持つ場合は、参照する版を明示してリンクします。手元で積み重ねてきた成果を公開するときは、必要なソースと教材を選び、出典、変更点、依存物の条件を記録します。

非公開の会話や私的な作業環境を前提とせず、公開されたコードと資料から内容を確かめられるようにします。別作品のソースや素材についても、元の出典とライセンス条件を尊重します。

## 何が分かったと言えるか

実装できたことと、正しく動くことは同じではありません。

検査が通ったことと、実機で動いたことも違います。実機で動いたからといって、人が遊びやすいと感じることや、別の作品でも同じ設計が役立つことまで分かるわけではありません。

このリファレンスでは、次のような結果を区別して扱います。

- **実装したこと** — コードとして何が存在し、どのように構成されているか。
- **検証したこと** — どの条件を、どの方法で確かめたか。
- **実際に観測したこと** — 特定の環境や実機で、どのような挙動を確認したか。
- **考察していること** — 実装や有限の例から何が考えられ、どの条件がまだ必要か。
- **まだ分からないこと** — 未検証の範囲、残る反例、異なる作品への適用可能性など。

形式手法や有限の実験を使う場合も、前提と適用範囲を明らかにします。検査に失敗した例や、意図した性質が成り立たなかった反例も、次の設計を考えるための重要な材料です。

数学的な表現が得られたことと、一般のゲームに使える仕組みが完成したことも区別します。理論的な考察を深めながら、実際のコードと具体例に立ち返って確かめていきます。

## 探究の現在地を更新する

ここに並ぶ内容は、過去に完成したものだけではありません。いま試している表現や、まだ解決していない問いも含まれています。

新しい知見が得られたら、関連する実装や検証結果を確かめ、既存の主題へ整理して加えます。結果が以前の考えを変えることもあります。その場合は、何が変わり、なぜ見直したのかを辿れるようにします。

将来、共通のライブラリやゲームエンジンとして取り出せる構造が育つかもしれません。一方で、作品ごとに異なる設計を残すほうがよい場合もあります。

その結論を先に決めることなく、使える成果と開かれた問いを積み重ねていきます。

fp-game-alphaは、そうした技術探究と実践の現在地を、実装から辿れるようにする場所です。
