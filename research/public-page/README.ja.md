# 「壊れないゲーム開発」を伝える公開ページ

2026年10月4日。公開ページの設計判断と、その根拠を残すノートです。
読者の理解や制作成功を実測した報告ではありません。

## 誰が、何を始めるためのページか

中心となる読者は、AIと自分のゲームを作りたい個人開発者です。
Haskellの経験は問いません。読み終えた人が、自分のAIへ企画を渡して
ゲーム制作を始めることを目指します。

中核は「壊れないゲーム開発」です。ゲームで守りたいルールを明確にし、
型、純粋な状態更新、検証で支える。AIには、その設計と確認の進め方を渡します。
これは、AIが間違えづらく、効率よく制作するための思考の枠組みを作る試みです。
現時点で全ゲームの無欠陥や、一定の生産性向上を実証したという意味にはしません。

長期の目的は純粋関数型ゲームエンジンです。異なるゲームを作りながら設計と
共通APIを磨き、いま使える部分をαとして公開します。
[研究の目的](../../docs/purpose.md)と[新作を作る手順](../../docs/new-game.md)を、
ページの説明と開始案内の基準にしています。

今回の設計を考え直す材料として使っています。

## このプロジェクトに固有の仮説

**ゲームの操作で守るルールを理解し、そのルールをコードがどう扱うか確かめられれば、
AIへ渡す設計手順の価値を、自分の企画に結び付けやすい。**

そのため、説明の順序を「具体的な操作と拒否 → 型・状態更新・検査 → AIが使う判断手順
→ 自分の企画で開始する」としました。読者は開始ボタンやソースリンクから必要な場所へ
直接進めます。この順序は設計仮説であり、読者テストで優位性が確定したものではありません。

検討した入口は三つあります。

| 入口 | 得られるもの | 懸念と採否 |
| --- | --- | --- |
| ゲームの操作と、変更後も守るルール | Haskell未経験でも、設計が作品に何をもたらすか考えやすい | 小さな例を全体保証に広げない説明が必要。主な入口に採用 |
| 型・反例・保証の詳細 | 技術的な根拠へすぐ到達できる | 制作の入口が研究目録に埋もれやすい。各例から詳しく読む経路として採用 |
| AIに渡す思考の手順 | 規約と検査を整えるという独自性が直接伝わる | 抽象的な方法論だけに見えやすい。実例の直後へ接続 |

### 実物との対応

| ページの説明 | 実物 | 読み替えてはいけない範囲 |
| --- | --- | --- |
| 前の手番の再送で次の依頼を進めない | [Station入力処理](../../references/station/app/HeadlessMain.hs)、[Domain](../../references/station/src/Station/Domain.hs)、[公開用実行記録](../../site/evidence/station-trace.json) | 記録の拒否は入力プロトコルの照合。Domainの古いTurnId拒否は別の検査。全UIの二重操作や保存競合を保証しない |
| 失敗した操作では旧状態を保つ | [Station Adapter](../../references/station/src/Station/Adapter.hs) | 純粋コアの状態と、ホストが行う描画・保存の成功を区別する |
| 外から状態を直接書き換えさせない | [Lantern](../../references/lantern/src/Lantern.hs)、[外部利用者のコンパイル検査](../../tools/test_lantern_api.py) | 正常な利用がコンパイルできた後、意図した診断で負例が拒否されることを確認する。内部コードやunsafe操作の全般まで証明しない |
| 異なる資源の量を型で区別する | [Quantity](../quantity/README.md) | 型の区別、値の範囲、有限検査、過去のLiquidHaskell検査は別々の根拠 |
| 作った後も作品を変更する | [Paper Circuit](../../references/paper-circuit/README.md)のUndo追加と読みやすさ改善 | 実ブラウザの操作確認が未完了であることを作品紹介の近くに表示 |
| 純粋なルールを実際の画面と音へつなぐ | [Afterlightの日本語ガイド](https://m-simplifier.github.io/garden-of-afterlight/guide/) | 別作品の画面だけで、新作導入経路の受入れや全端末対応を示したことにしない |

Stationの表示は、実際のHaskell実行から得た三つの応答を再生します。
JavaScriptへゲームのルールを移植して、元の実装の証拠に見せる方式は採りません。
参照コミット、入力、応答、ソースの指紋はJSONに残しています。

Afterlightの文章改善からは、ゲームの具体的な動作を説明してから実装へ進む書き方を
採りました。[改善コミット](https://github.com/M-simplifier/garden-of-afterlight/commit/c4ae4cc6ccd6dbc33162396a13ce944a28d11b08)
と公開ページを確認しています。文章変更が一般の読者理解を改善したという比較実験は
行っていません。画面とコードを結び付ける方法を、今回の内容に合わせて使います。

## 「効率的」を今どう扱うか

目指すのは、正しさに関する判断の再発見や、不適切な設計で進んだ後の手戻りを減らす
ことです。型は受け付けられるプログラムを制限し、検査は想定した失敗を露出させます。
規約と実装例は、どの機構を使うかをAIが判断する材料です。
これらはモデル内部の思考改善を観測したという主張ではありません。

今後の比較では、同じモデル・環境・権限・予算で、新規企画と既存作品の変更を分けて
評価します。完成率だけでなく、仕様の保持、不正操作の検出、検査の弱化、手戻り、
実行時間・費用を記録します。公開例の再生だけを成功課題にせず、別の企画でも確かめます。
技能の読取回数や追加文書量だけでは効果を判定しません。

## 公開と、これからの確認

αでは、現在のコードと根拠を公開し、読者が自分の企画で試す道を用意します。
全エンジン・全OS・全研究の完成を、紹介ページの公開条件にはしません。
一方、特定のAI・対象で制作経路を「確認済み」とする場合は、その組合せで
企画、最初のプレイ、一回の変更、新しいセッションでの継続を確認します。

ページのコピー文は、取得した参照コミット、技能の実ファイル、GAME-SPEC、独立した
保存先、実行確認、継続案内をAIへ指示します。コピー成功だけでは、技能の読取や
ゲーム制作の成功を示しません。入力した企画はこのページから送信・保存しません。

読者による確認では、「何を守る仕組みか」「自分のゲームで何を守りたいか」
「使いたい対象で何が未確認か」を本人の言葉で説明できるかを見ます。
開始できなかった場合は、文面、技能発見、権限、ツールチェーン、ゲームの実装、
対象ホストのどこで止まったかを分けます。クリック数だけで原因を決めません。

現在のページの表示・操作・公開検査は [site/README.md](../../site/README.md) に記録します。
人間の初心者による理解・導入評価、AIをまたぐ転移、生産性の比較は今後の検証です。
