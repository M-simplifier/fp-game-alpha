# 作ったゲームのコードをAIと読む

遊んでいるときの「なぜこう動くのか」を、そのゲームの型と関数から読み解くための
`learn-code`です。Haskellの文法を先に一通り学ぶ必要はありません。
たとえば、残り体力が減る処理や、一度使った操作を拒否する処理を選び、
実際のコードを少しずつ読めます。

ゲームのフォルダーをAIに開いてもらい、次のように伝えてください。

> `$learn-code` このゲームで、操作を受け付けてから画面が変わるまでを知りたいです。
> Haskellは初めてです。まず一つの操作を、実際の型と関数を使って説明してください。

「この型の矢印は何を表すの？」「Undoでどの値が戻るの？」「このルールを変えるなら
どこを読むの？」という質問から始めても構いません。すでに分かっている部分は省きます。
短い実例として、[Stationの各駅便を読む解説](https://github.com/M-simplifier/fp-game-alpha/blob/6526ef6/docs/learn-code-station.ja.md)も用意しています。

以下は、解説を担当するAIのための手順です。

## 読者が遊んだ動きと、現在のソースを対応させる

作業対象のルート、仕様、ビルド設定、現在のソースを確認します。独立して作られたゲームや、
利用者が改造したゲームも対象です。参照ゲームの構成をそのまま当てはめないでください。
対象が決まっていれば、経験年数などの質問を並べず、まず一つ説明を始めます。
Haskellが初めてという前提は、他のプログラミング経験までないという意味ではありません。

プレイヤーがした一つの操作を選び、その入力を作る箇所、ルールを判断する関数、
状態を受け取る呼び出し側、表示や効果へ渡す箇所を探します。入口の名前だけで推測せず、
実際の呼び出し関係を確認してください。保存やUndoが質問なら、その往復も追います。

説明に使う定義は、ファイルのパスと関数・型の名前で示します。必要なら現在の行番号を
添えます。Gitの版や変更中のファイルを確認できる場合は、どのコードを読んだか短く残します。
版を取れなければ、その事実を示せば十分です。過去の解説と食い違うときは現在のソースを
読み直し、推測で穴を埋めません。

既に使える構造化readerや型の表示機能があれば利用できます。結果が途中で切れている、
未保存の編集を含まない、型が不明と表示される、といった限界は元ファイルや必要な
コンパイラ確認で補います。通常のファイル読取でも解説は始められます。
読書のためだけに、新しいエディタや依存関係の導入を必須にしないでください。

## 小さいコード片を、ゲームの値で読む

最初に「この操作で何が変わり、何が変わらないか」を一文で示し、対応する実際の型と
短いコード片を置きます。型だけで分岐や計算の内容を説明せず、必要な実装まで読みます。
引用を省略するなら省略位置を明示し、説明用に書き換えたコードを原文と混ぜません。

記法は、そのコードに出てきたときに説明します。たとえば `a -> b` は入力と結果、
`Maybe` は値がある場合とない場合、`Either` は二種類の結果を区別する型として扱い、
このゲームではそれぞれに何が入るかを示します。`Left` が失敗を意味するかどうかも、
その関数の使い方で確かめます。変数名を日本語に訳すだけで終えないでください。

状態を返す関数なら、実際の初期値や一場面を使って、入力・変更前・変更後を並べます。
純粋関数が新しい値を返すことと、外側のループが次に使う値を選ぶことを分けます。
失敗を返した関数の型だけから「ゲームが変わらない」と断定せず、呼び出し側の分岐まで
たどります。効果のデータを作る処理と、実際に描画・再生・保存する処理も区別します。
`do` があっても、直ちに入出力をしているとは説明しません。

最初からすべての抽象化、モジュール、言語拡張を教える必要はありません。
読者が理解したい動きを説明するのに必要な範囲から広げます。読み慣れてきたら、
短くした理由や、別の設計と比べた利点・不利点まで扱えます。

## 型と、実行時の判断と、検査結果を分ける

次の区別は、実際のソースに当てはまるものだけ説明します。

| 確認する場所 | 説明する内容 |
| --- | --- |
| 型の宣言 | どんな入力と結果を表すか。異なる種類の値を区別できるか |
| exportと公開API | 利用側が作れない・書き換えられない値は何か。読み取り用の値との違い |
| 関数の分岐 | 体力不足、古い操作、範囲外の値などを、どの条件で拒否するか |
| 呼び出し側 | 成功・失敗の後、どの状態を次に使い、何を表示・実行するか |
| テスト・実行記録 | どの入力、法則、環境で何を確認したか。未実行なら未実行と示す |

コンパイルが通ること、有限のテストが通ること、形式的に示された性質、実際の画面で
確認したことを同じ保証にまとめません。通常の型や `newtype` の名前だけで、数値の範囲や
時間的な正しさまで証明されたとは説明しないでください。

## 次の一場面を考えて、理解を確かめる

説明したあと、同じルールが別の入力でどう働くか、一つ予想できる例を添えます。
読者が望めば、自分の言葉で説明してもらったり、小さな変更を一緒に試したりできます。
質問への回答を待つだけで解説を止めたり、すべての回を試験形式にしたりする必要はありません。

変更を試す場合は、何が変わると予想するか、どのソースを変えるか、どの観察や検査で
確かめるかを対応させます。解説依頼だけなら元のゲームを書き換えず、変更案として示します。
利用者が変更を依頼しているなら、その範囲で実装・確認を進めます。

コード読取から導いた予想と、実際に実行した結果を明示します。AIによる解説や模擬的な
読み取りができても、人間の理解が確認できたことにはなりません。続けるときは、
読者が何を分かっていて次に何を知りたいかを会話から更新します。

## 別のゲームへ持っていく

AIが独立したゲームを作るときは、スキル本体とこの案内、Stationの実例をそれぞれ
`.agents/skills/learn-code/SKILL.md`、`docs/learn-code.md`、
`docs/learn-code-station.ja.md`へコピーすると、同じ相対リンクで使えます。
配布元のMIT表記と取得した版も残してください。既存の同名ファイルを上書きせず、
そのゲームの継続用スキルや案内から学習の入口をたどれるようにします。

Stationの公開ソースへのリンクは参考文献であり、ゲームのビルド依存ではありません。
オフラインでも対象ゲームのローカルソースを読めます。スキルのあるフォルダーを開けば
すべてのAI製品が自動認識する、という前提にはせず、必要ならスキル本文をAIに指定します。
